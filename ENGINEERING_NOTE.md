# FinchPay engineering note

**Execution on `2468`.** Triage has normalized the requested charge, classified intent, and handed CH-101 to Identity. The shared server session is waiting and unverified. The message route in src/server.ts locks that session and awaits runTurn in src/loop.ts. Identity in src/agents.ts accepts only a four-digit candidate, requests verify_identity, and consumes its result. Only success permits the verified-state update and handoff to Refund. A repeated request or question is re-prompted without calling the verifier or consuming the one allowed failed-code attempt.

Refund requests issue_refund for the stored charge. **MockTools.issue_refund in src/tools.ts checks the verified flag and a private, session-object-bound successful-verification marker before any refund-map write.** Customer claims, model outputs, and forged flags alone cannot authorize a refund. It validates the charge, then checks a process-wide charge ledger. A new record returns created=true; an existing record returns the same reference with created=false and no write. Refund's deterministic message distinguishes “issued” from “already refunded.” The loop stores the reference/outcome, marks ended, replies, and returns. The server releases its lock in finally. Waiting also returns immediately; resumed turns are bounded to 12 actions. Ended sessions do not run again.

**Design choice and alternative.** Triage uses an exact-command parser, Decisions intent classification with recent conversation context, and Responses-generated clarification/process replies. A general model controlling tools would be more flexible, but classification and wording are separated from authority here. The strict command refund ch101 is normalized and handled directly; longer language uses Decisions. Confidence below 0.8 asks for clarification in the same chat rather than lowering the cutoff or forcing a restart. The cutoff is provisional, not calibrated proof. Responses produces a bounded JSON message without tools; errors fall back to guided wording. Identity prompts and refund confirmations stay deterministic. OPENAI is loaded from .env only on the server.

Cross-chat deduplication is an extension, not an assignment requirement. New chat resets transcript and verification because verification is session-scoped. It does not reset the charge ledger. A second chat must verify again, then receives the existing refund reference without another payment. Clarification retains the current conversation, so New chat is reserved for an intentional fresh session or an ended conversation.

**Concrete limitation and first improvement.** Restarting the local server clears the in-memory charge ledger. The same mocked charge can then be refunded again. Real payments need durable customer/charge eligibility plus a provider idempotency key checked atomically at the action boundary. Identity is still a shared mock code, and generated wording can be wrong despite schema validation and display filtering.
